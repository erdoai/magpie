*Consistency starts here: a KV key is the single canonical home for a value, so every entry that references it quotes one true value — change it once, and everywhere it's referenced follows.*

Some knowledge isn't prose — it's a **value**. A feature flag, a rate limit, a support email, a set of brand colors, the current pricing tier. A **KV store** is a named key/value store for exactly that: structured context an agent reads whole by key, not by search.

KV stores are standalone (not owned by an entry) and scoped by org / workspace / project, addressed by a `slug`.

```bash
magpie kv set config support_email --value '"help@example.com"' --type string
magpie kv set config trial_days --value 14 --type integer
magpie kv set config signups_open --value true --type boolean
magpie kv get config trial_days
```

## Typed values

Each key declares a `value_type`, validated on write and returned on read, so agents deserialize without guessing:

| `value_type` | Accepts |
|--------------|---------|
| `json` | Any object/array (the default) |
| `string` | A JSON string |
| `integer` | A whole number (not a bool) |
| `float` | A number |
| `boolean` | `true` / `false` |
| `datetime` | An ISO 8601 string |

A value reference like `{{config.trial_days}}` in an entry then resolves to an actual number, not a string — see [Links & references](/concepts/links).

## Two layers: live vs curated

KV stores have a `source` that decides where the truth lives:

- **`server`** (default) — live, agent-written runtime data (metrics, resolved facts). The server is canonical.
- **`repo`** — curated data (config, brand tokens, definitions) owned by a [bundle](/repo-sync/overview) in git. The file is canonical; the server **rejects** agent/API writes to these stores, so they can't drift from the repo.

This keeps runtime values out of version control and curated values reviewable in pull requests. See [Repo KV stores](/repo-sync/kv).
