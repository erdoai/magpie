title: Collections
description: Typed JSON key/value stores for structured context read whole by key.
---

Some knowledge isn't prose — it's a **value**. A feature flag, a rate limit, a support email, a set of brand colors, the current pricing tier. A **collection** is a named key/value store for exactly that: structured context an agent reads whole by key, not by search.

Collections are standalone (not owned by an entry) and scoped by org / workspace / project, addressed by a `slug`.

```bash
magpie collections set config support_email --value '"help@example.com"' --type string
magpie collections set config trial_days --value 14 --type integer
magpie collections set config signups_open --value true --type boolean
magpie collections get config trial_days
```

## Typed values

Each document declares a `value_type`, validated on write and returned on read, so agents deserialize without guessing:

| `value_type` | Accepts |
|--------------|---------|
| `json` | Any object/array (the default) |
| `string` | A JSON string |
| `integer` | A whole number (not a bool) |
| `float` | A number |
| `boolean` | `true` / `false` |
| `datetime` | An ISO 8601 string |

A value reference like `{{config.trial_days}}` in an entry then resolves to an actual number, not a string — see [Links & references](/concepts/links).

## Two layers: live vs curated

Collections have a `source` that decides where the truth lives:

- **`server`** (default) — live, agent-written runtime data (metrics, resolved facts). The server is canonical.
- **`repo`** — curated data (config, brand tokens, definitions) owned by a [bundle](/repo-sync/overview) in git. The file is canonical; the server **rejects** agent/API writes to these stores, so they can't drift from the repo.

This keeps runtime values out of version control and curated values reviewable in pull requests. See [Repo collections](/repo-sync/collections).
