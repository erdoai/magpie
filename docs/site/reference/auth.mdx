This page is the integration reference: how a request proves who it is, how the **active org** is chosen, and how to connect a new project so its knowledge lands in the right place.

For the conceptual model (orgs vs workspaces vs projects, when to use a separate org), see [Multi-tenancy](/concepts/multi-tenancy).

## How a request authenticates

A request identifies itself one of two ways:

| Method | Header / cookie | Used by |
|--------|-----------------|---------|
| **API key** | `Authorization: Bearer <key>` | CLIs, MCP, scripts, services |
| **Session** | `magpie_session` cookie | the web app (email one-time-code login) |

The **user** is always derived from the trusted token or session — never from a client-supplied value. You cannot impersonate another user or org by setting a header.

When both `API_KEY` and `RESEND_API_KEY` are unset, auth is disabled (single-user local dev): every request runs as an unrestricted, single-tenant context.

## The active org

A user can belong to many orgs but acts in one at a time. The active org is resolved, in order:

1. **`X-Organization-ID` header** — an explicit choice, **validated against your membership**. Naming an org you don't belong to returns `403` (it is never silently ignored).
2. **Saved default** — set with `POST /api/orgs/{id}/select` (or `magpie org use`). Stored per user; self-heals if you later leave that org.
3. **First membership** — a sensible bootstrap when you've set nothing.

```bash
# Read entries as they appear in the "acme" org
curl -H "Authorization: Bearer $MAGPIE_TOKEN" \
     -H "X-Organization-ID: acme" \
     https://magpie.example.com/api/entries
```

### API keys and the active org

- A key **pinned to an org** (the default when you create one) acts in that org. `X-Organization-ID` can still switch it to **another org you're a member of** — but the key's role is a **ceiling**: switching never grants more than the key was issued with.
- A key with **no pinned org** falls back to your saved default / first org, or honours `X-Organization-ID`.

This means one personal key can serve several orgs — point it with the header rather than minting a key per org.

## Roles

Roles are hierarchical: `viewer` < `editor` < `admin` < `owner`. Enforcement lives in the REST API (the single source of truth); every client inherits it.

| Action | Minimum role |
|--------|--------------|
| Read / search | `viewer` |
| Write / archive / merge entries, set documents, attachments | `editor` |
| Manage members & workspaces | `admin` |
| Delete the org | `owner` |

A key can never be created with a role higher than the caller's own.

## Security model

- **Fail-closed reads.** Entry/KV-store/pair lookups filter visibility in SQL. A cross-tenant fetch by ID returns nothing — the isolation does not depend on the application remembering to check.
- **Org is the wall.** Workspace and project are filters within a trusted org boundary, not security boundaries (see [Multi-tenancy](/concepts/multi-tenancy)).
- **Identity is trusted, org hints are validated.** `X-Organization-ID` is a hint checked against membership on every request.

<Warning>
**Static-key mode is single-tenant.** A request authenticated with the static `API_KEY` is unrestricted and sees everything. Do not use static-key mode on an instance that holds more than one org's data — issue per-user keys (or use session login) instead.
</Warning>

## Connect a new project

1. **Get a key.** `magpie login` (email one-time-code) mints a personal API key and stores it in `~/.config/magpie/`. Or create one with `POST /api/keys`.
2. **Pick the org.** `magpie org list`, then `magpie org use <org>` to set the active org for this machine (sent as `X-Organization-ID` and saved as your default). The active org is marked in `magpie whoami`.
3. **Pick the workspace/project.** `magpie link --workspace <ws> --project <proj>` sets defaults so this repo's knowledge is filed consistently.
4. **Use it.** CLI commands, the [stdio MCP server](/mcp/setup), and direct REST calls all run in that org/workspace/project.

Environment overrides (handy for CI and services): `MAGPIE_TOKEN`, `MAGPIE_ORG`, `MAGPIE_API_URL`.

```bash
magpie login
magpie org use acme
magpie link --workspace mobile-app --project checkout
magpie whoami        # confirms active org + linked scope
```
