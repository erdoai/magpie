Most commands accept `--workspace` and `--project` to scope, falling back to what you set with `magpie link`. They run against your **active org** — see [Authentication & multi-tenancy](/reference/auth).

## Auth & account

```bash
magpie login              # email one-time code → store an access token
magpie logout             # remove the stored token
magpie whoami             # server, auth, active org, linked scope, orgs
magpie link --workspace support --project billing
magpie workspace list <orgId>
```

## Orgs, workspaces & projects

A user can belong to several orgs but acts in one at a time. `org use` sets the active org for this machine — sent as `X-Organization-ID` and saved as your server-side default.

```bash
magpie org list                       # your orgs (active one marked with *)
magpie org create <name>              # create an org and switch to it
magpie org use <org>                  # set the active org (id or slug)
magpie org current                    # show the active org
magpie org clear                      # fall back to your default
magpie org invite <org> <email> --role editor   # add a member (admin+)

magpie workspace list <orgId>
magpie workspace create <orgId> <name>           # create a workspace (editor+)

magpie project list <workspaceId>
magpie project create <workspaceId> <name>       # create a project (editor+)
```

Override the active org per-invocation with the `MAGPIE_ORG` environment variable.

<Note>
**The hierarchy is org → workspace → project.** Workspaces and projects are registries you can pre-create for listing and navigation, but neither is required before writing — tagging an entry with a new workspace/project slug is enough to start using it. "Switching" means setting your default scope with `magpie link --workspace <ws> --project <proj>` (or passing `--workspace`/`--project` per command). They organise knowledge within a trusted org; they are **not** security boundaries — see [multi-tenancy](/concepts/multi-tenancy).
</Note>

## Knowledge

```bash
magpie search "incident runbook" --workspace support --tags runbook
magpie read <entry-id> --resolved          # resolve {{refs}} and [[links]]
magpie write --title "Refund policy" --file refund-policy.md \
  --tags policy,billing
magpie write --title "Refund policy" --file refund-policy.md --dedupe   # update closest match
magpie archive <entry-id>
```

`write` takes `--file <path>` or `--content <text>`. Pass `--dedupe` to update the closest existing entry instead of creating a near-duplicate.

### Recent activity

```bash
magpie updates                          # what changed across the store, newest first
magpie updates --workspace support --limit 50
magpie history <entry-id>               # previous versions of an entry
magpie history <entry-id> --full        # include each revision's full content
```

`updates` reads the durable [activity log](/concepts/activity) — entries, KV, attachments, merges, bulk edits, and bundle pushes — showing what changed, when, and by whom. It survives overwrites and deletes. `history` shows an entry's previous versions (title/content/tags/source before each meaningful edit), newest first.

### Staying coherent

```bash
magpie duplicates --workspace support               # cluster near-duplicate entries
magpie duplicates --threshold 0.08 --limit 100      # stricter, wider scan
magpie merge <id-a> <id-b> --title "Refunds" --file merged.md
```

`duplicates` reports clusters of entries that cover the same ground by semantic similarity (lower `--threshold` is stricter). `merge` collapses two or more into one — you supply the synthesized `--title` and `--file`/`--content`, and the sources are archived with lineage. See [Staying coherent](/concepts/coherence).

### Reorganizing in bulk

```bash
magpie rescope --workspace reach --to-workspace erdo            # preview a move
magpie rescope --workspace reach --to-workspace erdo --apply    # commit it (admin)
magpie rescope --project alertee --clear-project --apply        # retire a project namespace
magpie retag --workspace support --rename old=new --apply       # rename a tag everywhere
magpie retag --tag legacy --add imported --remove legacy --apply
```

`rescope` moves matched entries to a new `--to-workspace`/`--to-project` (or `--clear-project`); `retag` does `--add`/`--remove`/`--rename old=new`. Both select with a required `--workspace`/`--project`/`--source`/`--tag` filter and are **dry-run unless `--apply`** — applying needs the `admin` role. Changes are in place, so ids and links survive. See [Reorganizing in bulk](/concepts/bulk-operations).

## KV stores

```bash
magpie kv list
magpie kv get config trial_days
magpie kv set config trial_days --value 14 --type integer
```

`set` takes `--value <json>` or `--file <path>`, and `--type` (`json`, `string`, `integer`, `float`, `boolean`, `datetime`). See [KV stores](/concepts/kv).

## Attachments

```bash
magpie attachments add <entry-id> ./logo.svg --role logo-primary --public
magpie attachments list <entry-id>
```

## Repo sync

```bash
magpie push ./knowledge --workspace support    # repo  → server
magpie export ./knowledge --workspace support   # server → repo
```

`push` validates the whole [bundle](/repo-sync/overview) and aborts on any off-spec file or drift issue. `export` writes entries, repo KV stores, a manifest, and a self-contained `index.html` viewer. See [Repo sync](/repo-sync/overview).
