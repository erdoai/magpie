---
title: Repo sync
description: Author knowledge as a folder of files in git, then sync it to the server.
---

Repo sync is docs-as-code for knowledge. You author entries and curated KV stores as plain files, review them in pull requests, and sync them to Magpie. **The repo is the source of truth; the server is the search and serving index.**

```bash
magpie push ./knowledge --workspace support     # repo  → server
magpie export ./knowledge --workspace support    # server → repo
```

Both commands exist in the [CLI](/cli/commands) and as REST endpoints (`POST /api/bundle/push`, `GET /api/bundle/export`). All parsing, validation, and anti-drift logic runs server-side — the clients only read and write files.

## Bundle layout

```
knowledge/
├── <entry>.md                  # markdown + frontmatter (entries)
├── kv/
│   ├── _manifest.json          # canonical store/key registry (anti-drift)
│   └── <slug>.json             # repo-canonical KV store: { key: value }
└── index.html                  # self-contained offline viewer (written by export)
```

## Path is identity

An entry is identified by its **relative path** in the bundle. Re-running `push` updates entries in place instead of creating duplicates — sync is deterministic, not a best-effort content match.

## Idempotent and atomic

`push` validates the whole bundle first. If any file is off-spec — bad [frontmatter](/repo-sync/frontmatter), an undeclared KV store, a near-duplicate slug — it **aborts and reports every problem**, leaving the server untouched. Nothing is written until everything is valid.

## The offline viewer

`export` also writes a self-contained `index.html` — open it in a browser, no server needed, to browse the bundle as a linked knowledge graph. It makes "your data is portable" tangible: a bundle plus one HTML file is a complete, browsable artifact.
