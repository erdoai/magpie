title: Repo collections

A repo-canonical [collection](/concepts/collections) is one JSON file under `collections/` — a flat map of key to value:

```json
// collections/config.json
{
  "support_email": "help@example.com",
  "trial_days": 14,
  "signups_open": true
}
```

The filename stem is the collection `slug`. On `push`, value types are **inferred** from the JSON natives:

| JSON value | Inferred `value_type` |
|------------|----------------------|
| `"text"` | `string` |
| `4200` | `integer` |
| `3.14` | `float` |
| `true` / `false` | `boolean` |
| object / array / `null` | `json` |

`datetime` is never inferred (it's indistinguishable from a string on the wire) — set it explicitly through the API if you need it.

## One file per store

Keep one file per store. It's readable, diffs cleanly in pull requests, and matches how a store is used (a named bag read by key). For a store that grows large or sees many editors, the directory form `collections/<slug>/<key>.json` is also accepted.

## Live vs curated

Pushing a repo collection creates it with `source: repo`. The server then **rejects** agent and API writes to it — the bundle is the source of truth. If a live (`source: server`) store already exists with the same slug, `push` refuses rather than clobber it. See [the two layers](/concepts/collections#two-layers-live-vs-curated).
